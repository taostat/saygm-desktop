# SayGM integration map

Use these boundaries when adding product changes or resolving an upstream merge.
The application still uses Goose's existing workspace, agent loops, ACP protocol,
provider interface and Electron lifecycle.

| Area | Product-owned code | Inherited integration points to review |
| --- | --- | --- |
| Backend identity | `crates/goose-provider-types/src/identity.rs` | Goose and local-inference prompt rendering, stock templates and fallback messages |
| Desktop runtime policy | `crates/goose/src/product.rs` | Config and secret storage, provider selection, startup and restricted auxiliary model paths |
| Inference provider | `crates/goose/src/providers/saygm.rs` | Provider registration and ACP provider inventory |
| Desktop product configuration | `ui/desktop/src/product/saygmProduct.ts` | Electron main, account service, onboarding and provider UI |
| Visual theme | `ui/desktop/src/styles/saygm-theme.css` | Stylesheet link order, the Tailwind token bridge in `styles/main.css`, and existing component markup |
| Account/OAuth | `ui/desktop/src/services/gmAccountService.ts`, `utils/gmAccountIpc.ts` | Main-process registration and the preload API |
| Inference guardrails | `services/guardrailsPolicy.ts`, `components/GuardrailsPanel.tsx` under `ui/desktop/src` | Account API contracts and settings navigation |
| Native packaging | Private Ubuntu/Windows workflows, `scripts/windows`, `scripts/build-ubuntu-release.sh` | Electron Forge configuration and native dependency changes |

## Invariants during an update

- SayGM stock prompt identity is independent of the desktop environment flag.
  Custom prompt content, tool names, protocol namespaces and `GOOSE_*` compatibility
  identifiers retain their existing meaning.
- Desktop policy preserves the existing config snapshot and per-call checks.
  Moving decisions must not introduce credential fallbacks or widen allowed providers.
- The renderer uses the existing account IPC interface; OAuth credentials stay in
  the main process and native secure storage.
- The SayGM stylesheet loads immediately after the shared stylesheet. Tailwind's
  `@theme inline` token-registration bridge stays in `main.css` so utilities are
  generated by the same pipeline. Theme extraction preserves cascade order.
  Component layout and translated
  product copy still need review when upstream changes those components.
- Windows helpers use SayGM-owned directories. Upstream tests that assume the
  old `GOOSE_NODE_DIR` override need isolated SayGM fixtures, not a relaxed policy.
- Shared code changes that cannot be expressed through these boundaries remain
  explicit downstream patches. Generic fixes can be proposed upstream separately.

This is a smaller set of places to maintain, not a guarantee of conflict-free
updates. The current changes do not turn all existing UI copy, packaging metadata,
or component structure into a configurable distribution framework.
